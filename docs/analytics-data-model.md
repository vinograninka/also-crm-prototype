# Аналитика ALSO CRM: правила для рабочей версии

Версия прототипа 4, 4 ноября 2026 года. Всё показанное реализуется обычными запросами к собственной базе CRM. Telegram нужен для переписки; расчёт продаж не зависит от наличия API аналитики у мессенджера. Этот документ описывает модель будущей серверной части, а не уже подключённый backend.

## Периоды

Начальная и конечная даты включаются целиком. Доступны любые корректные даты, один день, два дня, неделя, месяц, год и многолетний диапазон. «Месяц» означает с первого числа текущего месяца, «Год» — с 1 января. В макете быстрые кнопки привязаны к дате демо 03.11.2026; в рабочей версии конечную дату выдаёт сервер в часовом поясе компании.

На сервере события хранятся с временем в UTC. Для бизнес-дней используется единый согласованный часовой пояс, изначально Europe/Moscow; его выбор не зависит от страны сервера. Запрос использует полуоткрытый интервал от местной полуночи начальной даты до местной полуночи дня, следующего за конечной датой. Это включает конец последнего дня без искусственного времени `23:59:59` и не зависит от часового пояса браузера.

График группирует короткий период по дням, средний — по неделям, год — по месяцам, многолетний — по годам или группам лет. Группировка изменяет изображение, но не отсекает события и не меняет итогов. Количество столбцов ограничено; многолетний запрос не рисует тысячи элементов.

## Продажи и деньги

- Новая заявка: заказ, созданный в выбранном периоде.
- Продан заказ: заказ с первой подтверждённой оплатой или предоплатой в выбранном периоде. Одна первая оплата создаёт одну продажу.
- Продано тарифа: количество единиц сохранённых позиций каталога в таких заказах. Счёт без оплаты продажей не является.
- Поступило оплат: сумма отдельных подтверждённых платежей по датам поступления. В эту сумму входят доплаты по старым заказам, даже если их первая оплата была раньше выбранного периода.
- Конверсия: среди заявок, созданных в периоде, доля получивших первую оплату не позже конца периода. Продажи по более старым заявкам отображаются в продажах и поступлениях, но не подменяют знаменатель конверсии.
- Текущие этапы и ожидание ответа: текущее состояние заявок, созданных в периоде. Макет не выдаёт эти значения за реконструкцию состояния на прошлую дату.
- Сотрудники, внутренние служебные диалоги и спам исключаются из всех выборок. Сегмент — текущий сегмент клиента, как и раньше.

## Тарифы и состав заказа

Используются постоянные идентификаторы каталога из счетов. Тариф не определяется по названию проекта, похожей цене или тексту сообщения. Старые позиции с сохранённым ID остаются доступны для фильтра, даже если их уже нет в текущем каталоге. Заказы без связи с каталогом попадают в «Тариф не указан»; их неизвестное количество тарифов не выдумывается.

При первой оплате фиксируется состав продажи: ID и название товара/тарифа, количество, единица, цена, применённая скидка и итог. Изменение прайса, скидки клиента, нового черновика счёта или текущего состава заказа не переписывает этот снимок. Стоимость позиций после скидки распределяется с контролем округления, чтобы сумма строк совпадала со стоимостью заказа. В рабочей системе деньги хранятся целым количеством копеек или в точном decimal, без вычислений финансов через float.

Фильтр выбирает заказы, содержащие выбранный тариф. Денежный KPI показывает платежи **по всему такому заказу**, поскольку платёж может покрывать несколько позиций. Таблица тарифов показывает только выбранные строки и их стоимость после скидки. Это явно подписано в интерфейсе. Для распределения реальных платежей по отдельным строкам понадобилось бы отдельное утверждённое правило; прототип такого распределения не имитирует.

Один заказ может включать несколько тарифов и несколько единиц одного тарифа. В строках считаются количество единиц и число различных заказов с данной позицией. В общем итоге заказы считаются один раз, поэтому сумма построчных чисел заказов может быть больше общего числа.

Зафиксированный снимок описывает первоначальную продажу. Дополнительные продажи, отмены и возвраты в рабочей системе должны оформляться самостоятельными событиями и корректировками, а не бесследной перезаписью прошлого. Их полный интерфейс и правила не входят в текущий прототип.

## Хранение и расчёт в рабочей системе

Достаточны связанные таблицы:

| Данные | Ключевые поля |
|---|---|
| Заказы | ID, client_id, created_at, текущий этап, флаги спама/служебного контакта |
| Каталог | постоянный ID тарифа, название, единица, действующая цена, признак архива |
| Позиции заказа | order_id, catalog_id (может быть NULL), количество, сохранённая цена |
| Снимок продажи и его позиции | order_id, дата первой оплаты, неизменяемые позиции и суммы |
| Платежи | ID, order_id, paid_at, amount_minor, статус, метод, внешний ID провайдера |

Подтверждение платежа, создание первого снимка продажи и обновление оплаченной суммы выполняются в одной транзакции. У внешнего платежа должен быть уникальный ключ `(provider, external_id)`: повтор webhook не создаёт повторную оплату. Ручная отметка тоже имеет уникальный ID. Неподтверждённые платежи в отчёт не попадают. Права руководителя проверяет сервер; переключатель роли в HTML остаётся демонстрацией.

Реализация использует фильтры дат, `SUM`, `COUNT(DISTINCT order_id)`, группировку по catalog_id и индексированные даты. API отчёта принимает даты и ID тарифа и возвращает одновременно итоговые показатели, таблицу тарифов, группы графика и реестр заказов. CSV строится из тех же условий и модели, а не из отдельного «похожего» расчёта. Крупный период можно агрегировать в базе и отдавать постраничный реестр.

## Совместимость демо и проверка

Данные версий 1–3 сохраняются. Уже сохранённые документы, суммы и пользовательские изменения не переписываются. Для прежних демозаказов, где был только итог оплаты и одна сохранённая дата, миграция создаёт явно помеченную запись `legacy-summary`. Она сохраняет прежний итог, но не восстанавливает неизвестные реальные даты частичных платежей. В рабочем переносе для точной истории нужен исходный журнал платежей; по единственному текущему итогу его реконструировать нельзя.

Для проверки разных месяцев в прототип добавлены семь вымышленных архивных заказов за декабрь 2025 — ноябрь 2026 с явным составом и журналом платежей. Они доступны из реестра аналитики и истории клиентов, не засоряют текущую доску и чаты и не добавляются повторно при обновлении страницы. Названия и цены каталога остаются демонстрационными до получения настоящего прайса.

Автоматическая проверка: `node tests/analytics.cjs`. Проверяются включение границ, 29 февраля, переход года, длительные диапазоны, отсутствие пересечений групп, неподходящие даты, несколько тарифов в заказе, частичные оплаты, исключение спама и сотрудников, неизменяемый снимок, сохранность старых документов и соответствие CSV фильтру. Браузерная проверка отдельно подтверждает работу формы и вида на телефоне.
